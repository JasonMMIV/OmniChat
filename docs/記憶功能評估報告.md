# OmniChat 記憶功能評估報告

> **評估日期**：2026-11-05
> **評估範圍**：助理記憶（Assistant Memory）子系統——資料模型、儲存、工具、提示注入、UI、備份同步、測試與文件。
> **依據**：《OmniChat 專案開發與維護手冊》v1.27.0 與現行原始碼逐檔核對（檔案與行號見各節）。
> **結論**：功能可用但治理不足；有 2 項會實際影響正確性的缺陷（P0），另有數條違反專案自訂契約的實作，且全功能零自動化測試。建議改進。  
> **後續（2026-11-06）**：本報告的 P0–P3 已由《記憶功能改善實作計畫（已實作）》處理；實作與驗證結果見該計畫 §0.6。

---

## 一、現況梳理

| 面向 | 現況 | 位置 |
|---|---|---|
| 資料模型 | `id` / `assistantId` / `content` 三欄，**無時間戳** | `lib/core/models/assistant_memory.dart` |
| 儲存 | SharedPreferences 單一 JSON 字串 `assistant_memories_v1`（SQLite 遷移管不到） | `lib/core/services/memory_store.dart` |
| 工具 | `create_memory` / `edit_memory` / `delete_memory`（僅 `enableMemory && supportsTools` 時註冊） | `tool_handler_service.dart:218,394-452` |
| 注入 | 記憶全文＋工具使用說明附加到 system 尾端 | `message_builder_service.dart:509-555` |
| UI | 助理編輯頁的開關＋逐條管理 | `assistant_settings_edit_page.dart:447-` |
| 備份 | 隨 settings snapshot 進備份（未列 `_localOnlyKeys`） | `backup_preferences.dart:35-44` |

**先講做得對的部分**：記憶隨備份走；compaction 層認得記憶工具名（折疊成短文，`history_compactor.dart:196-203`）；記錄內容不經過 32KB cap 是有意識的選擇（手冊 §3.14 §5 有如實記錄）；per-assistant 隔離與「最近聊天」一致。

**總評**：這是從 Kelivo 移植的最小可用實作。對照專案其他子系統（SQLite 底座、上下文四層治理、工具輸出上限、Agent Skills）的工程水準，記憶功能是明顯的「低治理」落差區——有 2 個會實際影響正確性的缺陷（P0）、數條違反專案自訂契約的實作，且**全功能零自動化測試**。值得改進。

## 二、問題清單（按嚴重度）

### P0-1 記憶會被靜默地漏注入（正確性 Bug）

`MemoryProvider.initialize()` **只**在助理編輯頁開啟時被呼叫（`assistant_settings_edit_page.dart:446`），而注入路徑直接讀快取：

- `message_builder_service.dart:516-517` → `mp.getForAssistant(assistant.id)` 讀 `_memories`

App 冷啟動後直接進入聊天 → provider 是空的 → **既有記憶整批消失於上下文**，無任何提示。直到 (a) 使用者開啟一次助理編輯頁，或 (b) 某輪真的呼叫了記憶工具（write 後 `loadAll()` 補上）。這正是「記憶功能」最不該發生的失效模式——靜默失憶。

**修法**：注入前兜底 `if (!initialized) await loadAll()`（或直接改讀 `MemoryStore.getForAssistant`），並補一條回歸測試。改動極小。

### P0-2 記憶工具回傳契約違反自家規範（手冊 §5.6）

`tool_handler_service.dart:1011-1027`：

- `create_memory` 成功**只回 content、不回 id** → 模型同一輪內無法知道該 `edit_memory` / `delete_memory` 哪個 id（記憶列表要下一輪重新注入才看得到）；
- `edit_memory` id 無效、content 空 → 回 `''`，與 `delete_memory` 成功時的 `'deleted'`（無效 id 也回 `''`）完全無法區分成功／失敗；
- 整段 `catch (_) {}` **吞掉例外且不寫 `FlutterLogger`**——手冊 §5.6 明文要求三條件（結構化 `tool_error` JSON＋不冒泡＋**同步寫入 logger**）。

**修法**：統一回 JSON（成功帶 `{id, action}`，失敗帶 `tool_error` 形狀），例外走 `FlutterLogger`。約 20 行。

### P1-3 `DateTime.now()` 每輪破壞提示快取

注入區塊包含「请使用绝对时间格式……当前时间是 `${DateTime.now().toIso8601String()}`」（`message_builder_service.dart:549`，原文為簡體），**微秒級、每輪必變**，且位於 system 訊息內部。前綴式快取（OpenAI 自動快取、Kimi／GLM context cache、Anthropic ephemeral，§3.5 是專案賣點）從 system 起**整個 prefix 失效**，長對話每輪重算、重新計費。

**修法**：時間戳降為日期粒度（當日內穩定，對「記憶含絕對日期」的訴求已足夠），或移出固定前綴區。順帶：目前是當地時間且無時區偏移資訊，可一併統一為 `{cur_date}` 的格式。

### P1-4 完全沒有規模治理

提示詞**鼓勵**模型主動記錄（「请主动调用工具记录，而不是需要用户要求」，原文為簡體），但：

- 單筆記錄無長度上限、總注入無上限、筆數無上限（`MemoryStore` 也不擋）；
- JSON 逐輪重新拼注入；記錄一多，token 成本與注入內容非線性成長，UI 列表同樣爆量。

對照：工具輸出有 32KB cap（§3.14 §5）、技能 description 有 1024 cap。**修法**：單筆 cap（如 2KB）、總注入 cap（如 32KB，尾部截斷＋提示）、筆數軟上限（如 200 筆，寫入時提示模型合併）。

### P1-5 `supportsTools` 閘門不一致

`tool_handler_service.dart:218` 只有支援工具的模型才註冊工具，但 `message_builder_service.dart:515` 注入只看 `enableMemory`——**不支援工具的模型也會收到「使用 `create_memory` 工具」的指令**，模型只能假裝它記住了。注入應與工具註冊同一閘門（無工具時只注入記憶本文）。

### P1-6 硬編碼簡體中文指令

`message_builder_service.dart:531-553` 整段提示詞硬編碼簡體中文（Kelivo 遺留），夾在英文 `## Memories` 標頭裡。與 AGPL 上游形態有關，但對 OmniChat 而言是工程債：

1. 非中文使用者的模型回覆語言會被偏置；
2. 與 l10n 體系脫鉤。

建議改 language-neutral 英文版（模型工具指令不應隨 UI 語系擺盪——同 `/skill` 投遞框架固定英文的先例，手冊 §3.15 §3）。

### P2-7 `<content>` 未轉義 ⇒ 持久化 prompt injection 載體

`message_builder_service.dart:527` 記憶原文直接進 system。模型（或使用者貼文內容）可以先說服模型把惡意指令存成記憶，之後**每一輪、每一個輔助模型**都會讀到。工作區／技能體系都有明確區塊與剝離規則，記憶沒有。最低成本修法：轉義＋區塊說明「記憶是資料不是指令」，逐筆照 `cap` 的慣例給上限。

### P2-8 記錄沒有時間戳

`AssistantMemory` 只有 id／content。提示詞要求模型「過時記錄應刪除」，但刪除決策需要的建立／更新時間完全靠模型自己寫進 content 文本（不可靠）。加 `createdAt` / `updatedAt`（可 NULL、向後相容，類 `WorkspaceConfig.previous` 的加欄慣例 §3.1）、UI 顯示與按年齡排序，成本很小、收益明確。

### P2-9 Merge 還原不同步記憶

`data_sync.dart:1104-1124`：overwrite 模式沒問題，但 **merge 模式對非 mergeable 鍵「已有即跳過」**——`assistant_memories_v1` 不在 mergeable 集合。跨裝置場景：B 裝置已有記憶鍵（哪怕舊值），A 裝置後來的記憶永遠合不進來；而且這是使用者資料，不是偏好。建議併入 mergeable 集合，並按 id＋assistantId＋content 去重合併。

### P2-10 語音路徑完全無記憶

`chat_turn_service.prepareTurnRequest`（`chat_turn_service.dart:253-302`）不注入記憶也不註冊記憶工具。語音對話是「記不住」的平行世界。至少讀側注入（無工具、純參考）成本低；工具側可維持不做。

### P3-11 兩條衛生問題（小）

- `MemoryStore.deleteForAssistant` 是**死碼**（零呼叫端）：刪除助理會遺留孤兒記錄，跟著備份永遠漂；
- `MemoryStore` 讀-改-寫整表無序列化保護，UI 與工具並發 `add` 存在 lost-update（agent loop 內串行所以罕見，但便宜一條 `Future` 佇列就能消掉）。

### P3-12 零測試＋手冊缺位

技能子系統有 133 條測試、連搜尋調度都有專測；記憶功能 glob `test/*memory*` 無任何東西，連 `MemoryStore` 的 id 分配都沒測。另外手冊 §3 沒有「記憶」章節（只在 §3.14 §5／§5.6 提了一筆）——按手冊自己的維護指引（新增核心功能模組 → §3），這是文件債。

## 三、建議落地順序

| 階段 | 內容 | 成本 |
|---|---|---|
| 先做 | P0-1 注入兜底、P0-2 工具契約＋logger、單元測試（各 1 檔） | 小 |
| 次做 | P1-3 時間戳降粒度、P1-5 閘門對齊、P1-6 英文化指令、P2-7 轉義 | 小-中 |
| 再做 | P1-4 三層 cap、P2-8 時間戳欄位（JSON 向後相容） | 中 |
| 視需求 | P2-9 merge 合併、P2-10 語音讀側、P3 衛生項、手冊 §3.x 章節補寫 | 中 |

## 四、建議刻意不做的項目（避免過度工程）

- **全域記憶銀行**（跨助理共享）：現行 per-assistant 隔離與「最近聊天」一致，先維持。
- **向量檢索／相關性篩選**：<200 筆規模下全文注入即夠。
- **自動摘要式記憶萃取**：引入額外 LLM 呼叫管線，收益／複雜度比差。
