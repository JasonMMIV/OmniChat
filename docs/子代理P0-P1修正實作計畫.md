## 0. 摘要

### 0.1 一句話

把子代理從「一次性、不可治理的 helper 工具」升級為「有 context 護欄、可真正中止、有具名 profile、可延續、可觀測」的委派機制；其中 P0-2 採**強制收尾輪**，確保任何預算停止都留下可用摘要。

### 0.2 目標

| 目標 | 對應 |
|---|---|
| 停止／逾時是執行層的停止，不是顯示層 | P0-1 |
| `max_steps`／`token_budget`／`timeout` 不再回空摘要 | P0-2 |
| helper 看得到專案規則與 workspace 座標 | P0-3 |
| helper 不會因 context 爆掉而整段失敗 | P0-4 |
| `role` 自由文字 → 具名、可限制權限的 profile | P1-1 |
| 使用者看得到 helper 做了什麼 | P1-2 |
| 多輪委派不必重送全部背景 | P1-3 |
| helper 用量計入父訊息 | P1-4 |
| 歷史 summary 不再每輪重放 24k | P1-5 |
| child 請求與父代 wire 真正一致 | P1-6 |
| summary 被標記為未信任資料 | P1-7 |

### 0.3 非目標（本輪不做）

- 背景 subagent／durable job／重啟恢復（P2）
- 真並行 fan-out（與 §5.1 never-parallel 衝突，P2）
- 完整 child session UI（本輪只做 trace，不做可導航的 child session）
- approval bubbling（child 審批提升到父時間軸）
- memory block 注入（本輪只注入 assistant standing instructions；memory 列 P2）
- 對話中的動態模型切換（本輪只允許設定頁預先指定；工具 schema 與聊天 UI 都沒有 model 參數）
- profile 的匯入／匯出與市集（本輪只做本機編輯器）

### 0.4 成功指標

1. 以 stub model 連續跑 20 次「每輪都呼叫工具」的 helper，`max_steps` 停止時 **20/20** 都有非空 summary，且 `summary_source=wrap_up`。
2. timeout 後，序列閘門在 in-flight tool 結束（或 5 秒 grace）前不放行；以計數器驗證任何時刻最多一個 helper 在執行工具。
3. read-only profile 即使被廣告了寫入工具，執行期仍回 `read_only_subagent`，無檔案變更。
4. 24k summary 的 replay stub ≤ 2.5KB，且 JSON 仍可解析。
5. 子請求的 wire capture 可見 `temperature`／`top_p`／`thinking_budget`／`session_id`／tool image policy。
6. 父訊息 `totalTokens` 包含 helper tokens；context 用量環不變。
7. 設定頁指定 agent 模型後，child 請求使用該 provider／model；未指定者沿用該次對話的模型；對話中無法覆寫。
8. 既有 17 案子代理測試全綠，`flutter analyze` 無新錯誤。

## 1. 現況與問題

### 1.1 目前資料流

```
parent tool loop
  └─ onToolCall('spawn_subagent')
       └─ _runSubagent
            ├─ SubagentSpec.fromArguments(task, role, max_steps)
            ├─ buildToolCallHandler(messageId: null, subagentContext: launch.child(childTools))
            ├─ SubagentRunner.run
            │    ├─ messages = [system(buildSubagentSystemPrompt), user(Task: ...)]
            │    ├─ runAgentLoop(maxSteps, tokenBudget, emitCalls: false)
            │    ├─ 每輪 AgentRoundFinishedEvent → buffer.clear()
            │    └─ SubagentOutcome(summary, status, steps, tokens)
            └─ ToolResultCaps.cap(toToolResultJson())
```

### 1.2 問題清單

| ID | 嚴重度 | 現象 | 根因 | 影響 |
|---|---|---|---|---|
| P0-1 | 正確性／安全 | timeout／停止後 helper 可能仍在跑工具；序列閘門已放行下一隻 | `_withDeadline` 只 cancel 訂閱、不 cancel transport；gate 在 `_run` 回傳即釋放 | 兩個 helper 同時改 workspace；「已停止」是假的 |
| P0-2 | 任務成敗 | `max_steps`／`token_budget` 時 summary 幾乎必為空 | 每個工具輪 `buffer.clear()`；kernel 在下一輪邊界才停 | 16～40 步成果全丟 |
| P0-3 | 品質 | helper 不知道 workspace 路徑、檔案地圖、專案規則 | system prompt 只有通用規則；未注入 `buildFileWorkspacePrompt`／`WorkspaceFileMap`／assistant prompt | 產出「看起來對但違反專案」 |
| P0-4 | 穩定性 | 大型工具結果幾輪後爆 context | runner 直接跑 kernel，無 L0／R0 主動護欄 | provider 400／413，helper 直接 error |
| P1-1 | 治理／安全 | `role` 是自由文字，無 tool allowlist／read-only | 只有 `task/role/max_steps` | helper 自稱 reviewer 卻能寫檔 |
| P1-2 | 可觀測性 | 只看得到最後 JSON，看不到 16 步過程 | `AgentRunFinishedEvent.messages` 被丟棄；無 trace extras | 卡住時無法診斷 |
| P1-3 | 能力 | 每次 spawn 從零開始 | 無 session／messages 保存 | 多輪委派重送全部背景 |
| P1-4 | 成本正確性 | helper tokens 只進 log／JSON | 未接入 `TokenUsage` | 用量與成本低估 |
| P1-5 | 成本／正確性 | 24k summary 每輪重放 | `spawn_subagent` 不在非重放集合，且無 replay 壓縮 | 歷史膨脹、引用過期結果 |
| P1-6 | 行為一致 | child 未帶 temperature/topP/thinkingBudget/toolImagePolicy/sessionId | `SubagentLaunchConfig` 缺欄位 | helper 行為不同、看不到圖、cache 失效 |
| P1-7 | 安全 | summary 直接當 tool result，無未信任標記 | 契約未標示 | helper 讀到的注入內容可能影響父代 |

### 1.3 為什麼 P0-2 採「強制收尾輪」

「只留最後 preamble 當 fallback」成本低，但 preamble 本來就是被設計丟棄的過程敘述，不是交付物。正確版是：

1. 主迴圈停止（`max_steps`／`token_budget`／`timeout`）時，保留 kernel 回傳的 `messages`。
2. 追加一則 **FINAL ROUND** user 訊息，明確要求「不得呼叫工具，現在寫最終摘要」。
3. 以 **text-only**（`tools: null`、`webFetchEnabled: false`、無 tool image policy）發一次請求。
4. 把該輪文字作為 summary；若失敗／空／逾時，才退回最後一個非空正文（preamble fallback）。
5. `status` 仍是 `max_steps`／`token_budget`／`timeout`，另加 `summary_source=wrap_up`、`partial=true`。

這樣做的代價是每次失敗多一個請求；換來的是整個任務的成果不會消失。以 16 步、10 分鐘的 helper 來說，這是合理的保險。

## 2. 設計決策

| # | 決策 | 理由 | 替代方案（不採） |
|---|---|---|---|
| D1 | P0-2 用強制收尾輪＋fallback | 保住成果；語義清楚 | 只留 preamble；直接丟棄 |
| D2 | 不改 kernel | 降低回歸風險；wrap-up 在 runner 內完成 | 在 kernel 加 final-round 狀態 |
| D3 | gate 等到 tool idle 或 5 秒 grace | 保證 §5.1；避免無限等待 | 永久持有 gate；立即放行 |
| D4 | profiles 先做 built-in＋儲存＋enforcement | 先解決治理與安全；UI 可後補 | 一次做完整編輯器 |
| D5 | replay 用壓縮 stub，不移除事件 | 保留連續性；控制大小 | 加入非重放集合 |
| D6 | helper tokens 進 `totalTokens`，不進 `promptTokens` | 成本正確；context 環不受影響 | 全部丟進 totalTokens；完全不相加 |
| D7 | session 只放記憶體（LRU 8／TTL 30 分） | 先解決多輪委派；避免持久化風險 | 直接寫 DB |
| D8 | trace 不存工具參數 | 避免 shell 指令中的秘密落盤 | 存完整 args |

## 3. 目標架構

### 3.1 執行流程（含收尾輪）

```
SubagentRunner.run
  ├─ gate.run(abort: cancelFuture)
  │    ├─ 若已取消 → 直接回 cancelled outcome（不進 gate）
  │    └─ _run
  │         ├─ messages = system(profile + brief + rules) + user(Task)
  │         ├─ loop = runAgentLoop(
  │         │      sendRound: guarded(sendRound),   // context guard + abort check
  │         │      onToolCall: guarded(onToolCall), // abort check + trace
  │         │      maxSteps, tokenBudget, emitCalls:false)
  │         ├─ 每輪：
  │         │    ├─ AgentRoundFinishedEvent → lastNonEmptyText = buffer; buffer.clear()
  │         │    └─ AgentRunFinishedEvent → finalMessages = event.messages
  │         ├─ 停止原因為 max_steps/token_budget/timeout 且 summary 空？
  │         │    └─ wrapUpRound(finalMessages + FINAL ROUND instruction)
  │         └─ 等待 in-flight tool settle（grace）→ 回 outcome
  └─ gate 釋放
```

### 3.2 新責任劃分

| 元件 | 責任 |
|---|---|
| `SubagentProfile` | 具名 profile：instructions／tool allowlist／readOnly／provider＋model／maxSteps／tokenBudget 上限 |
| `SubagentSpec` | 一次呼叫的參數：task／profileId／budgets／timeout／context window／sessionId |
| `SubagentRunner` | 主迴圈、context guard、wrap-up、trace、abort、gate、session messages |
| `SerialGate` | process-wide 串行；支援 queued abort |
| `SubagentSessionStore` | in-memory session（messages／profile／tokens／TTL／LRU） |
| `SubagentLaunchConfig` | 父代快照＋wire 參數＋brief 素材＋usage callback |
| `tool_handler_service` | profile 解析、brief 組裝、child handler、extras 持久化、session 存取 |
| `AgentOrchestrator` | 將 helper tokens 併入終態 `TokenUsage` |

### 3.3 狀態機

| status | 何時 | summary_source | partial |
|---|---|---|---|
| `finished` | 模型自然結束且有正文 | `final` | false |
| `max_steps` | 步數用盡 | `wrap_up`（失敗則 `preamble`） | true |
| `token_budget` | 預算用盡 | `wrap_up`（失敗則 `preamble`） | true |
| `timeout` | 主迴圈逾時 | `wrap_up`（失敗則 `preamble`） | true |
| `stopped` | 使用者停止 | `none`（不燒收尾請求） | false |
| `error` | transport／未預期錯誤 | `none` 或既有 partial | true |
| `empty` | 無正文且無法收尾 | `none` | false |

**status 判定優先序**：`cancelled` → `error` → `timedOut` → kernel stop reason。收尾輪成功或失敗都**不改變** status：`max_steps`／`token_budget`／`timeout` 即使 summary 落在 preamble／none，status 仍是原停止原因；`empty` 只保留給 `finished` 且三層 fallback 全空的情況。

### 3.4 與 kernel 的邊界

本計畫**不修改** `agent_loop.dart`。具體做法：

- context guard：包在 runner 注入的 `sendRound` 外層。
- abort-before-tool：包在 runner 注入的 `onToolCall` 外層；已取消時回結構化錯誤，不執行副作用。
- wrap-up：在 kernel 回傳 `AgentRunFinishedEvent` 之後，由 runner 另外發一次 text-only 請求。
- trace：在 `onToolCall` 外層計時與記錄。

## 4. 介面草案

### 4.1 `SubagentProfile`

```dart
class SubagentProfile {
  const SubagentProfile({
    required this.id,
    required this.name,
    required this.description,
    this.instructions = '',
    this.allowedTools,          // null = 全部（仍受 base exclusions）
    this.readOnly = false,
    this.providerKey,           // null = 沿用對話的 provider
    this.modelId,               // null = 沿用對話的 model
    this.maxSteps,
    this.tokenBudget,
  });

  final String id;
  final String name;
  final String description;
  final String instructions;
  final Set<String>? allowedTools;
  final bool readOnly;
  final String? providerKey;
  final String? modelId;
  final int? maxSteps;
  final int? tokenBudget;

  bool permits(String toolName);
}
```

內建 profile：

| id | readOnly | allowedTools | 用途 |
|---|---|---|---|
| `general` | false | null（全部 child tools） | 現行行為，預設 |
| `explore` | true | `file_read`／`file_list`／`file_info`／`file_search`／`file_grep`／`file_view_image`／`file_extract_text` | 唯讀探索 |
| `reviewer` | true | 同上＋`get_console_errors` | code review |
| `researcher` | true | 上述讀取工具＋`web_fetch`／`search_web` | 資料蒐集 |
| `coder` | false | null | 可寫入的實作 |

`readOnly` 是第二道防線：即使 allowlist 誤放，執行期仍拒絕寫入／shell。

模型綁定（A5）：`providerKey`／`modelId` 由設定頁預先指定；`null` 代表沿用該次對話。對話中不可覆寫，設定變更只影響之後的 spawn；跨 provider 的 child 不繼承父代的 `extraHeaders`／`extraBody`／`maxTokens`／`thinkingBudget`。

### 4.8 `SerialGate`

```dart
class SerialGate {
  Future<void> _tail = Future<void>.value();

  /// Returns null when [abort] fires before the turn is granted.
  Future<T?> run<T>(
    Future<T> Function() action, {
    Future<void>? abort,
  }) async {
    final previous = _tail;
    final release = Completer<void>();
    _tail = release.future;

    if (abort != null) {
      final granted = await Future.any<bool>([
        previous.then((_) => true),
        abort.then((_) => false),
      ]);
      if (!granted) {
        // FIFO invariant: the next waiter must still wait for the current
        // holder — release only after `previous` completes. Releasing early
        // would let the third waiter jump the queue.
        unawaited(previous.whenComplete(() {
          if (!release.isCompleted) release.complete();
        }));
        return null;
      }
    } else {
      await previous;
    }

    try {
      return await action();
    } finally {
      if (!release.isCompleted) release.complete();
    }
  }
}
```

不變式：

1. abort 勝出時**絕不執行** action（回 `null`，由 runner 轉成 `cancelled` outcome）。
2. abort 勝出時 release 必須等 `previous` 完成才完成，否則第三隻會跳過目前持有者直接開跑——與 bug 1 同等嚴重。
3. `run()` 回傳 `null` 與 `action()` 本身可能回傳的 `null` 要用不同型別或 sentinel 區分（本計畫用 `SubagentOutcome?`，action 永不回 `null`）。

**測試**

## 8. 風險與回滾

| 風險 | 影響 | 緩解 |
|---|---|---|
| 收尾輪多一次請求 | 成本／延遲 | 只在 3 種停止觸發；90 秒上限；`wrapUpTimeout=0` 可關 |
| gate 等 idle 卡住佇列 | 其他 helper 延遲 | 5 秒 grace；shell 先 cancel；`subagent_zombie` log |
| profile 限制誤傷既有 prompt | helper 少工具 | 預設 `general`；profile 只下修；錯誤訊息清楚 |
| 跨 provider 模型（A5） | 憑證缺失／模型不相容／成本歸屬不清 | 模型選擇器只列已設定的 provider；spawn 時 provider 無 config → `subagent_unavailable`；成本仍標「近似」 |
| brief 注入過多／衝突 | context 膨脹、指令衝突 | 分層＋上限；assistant prompt 加「工具指示可能不適用」 |
| trim 丟掉關鍵工具結果 | 摘要不完整 | tail-preserving trim；placeholder；`context_trimmed` 標記 |
| `subagentTokens` 影響統計 | 數字變動 | 只進 total，不進 prompt；測試 context ring 不變 |
| extras 過大 | DB／UI 負擔 | trace 40 筆、無 args、<8KB |
| session 記憶體 | 長跑膨脹 | LRU 8／TTL 30 分／不持久化 |
| per-run image policy | 圖片傳送增加 | 受 `sendToolImages` 與 vision 能力 gating |
| summary 注入 | 父代被說服 | `untrusted:true`＋tool description 明示 |

**回滾**

1. 使用者可在 Add-ons 關閉「Subagents」→ 工具不註冊。
2. `wrapUpTimeout=0` → 回到舊的「只回最後正文」行為（但仍保留 fallback）。
3. `agent` 預設 `general` → 工具集與現在相同。
4. profile storage parse 失敗 → 只用 built-ins。
5. replay 壓縮可單行回退（不影響 live 結果）。

1. **Durable session／背景 subagent**：job queue、重啟恢復、通知（與 P2-2 `BackgroundRunMonitor` 整合）。

6. **對話中動態模型切換**：允許主代理或使用者在對話中臨時改 helper 模型（本輪明確禁止）。
7. **Helper cost 精算**：解析每輪 `MessageUsage` 並累加（跨 provider 時的成本歸屬也在此處理）。
