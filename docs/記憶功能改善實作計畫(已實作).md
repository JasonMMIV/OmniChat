### 0.1 核定決策（2026-11-05，與專案負責人確認）

| 決策 | 選擇 |

### 0.2 結論

上游 kelivo 已於 2026-08-08 以三個 commit（[`59101ed`](https://github.com/Chevey339/kelivo/commit/59101ed) 資料模型與決定性 block builder、[`284d6eb`](https://github.com/Chevey339/kelivo/commit/284d6eb) 三舊工具 → V1 工具面、[`39c38ff`](https://github.com/Chevey339/kelivo/commit/39c38ff) 背景整理 pipeline＋設定頁）把記憶功能從「三工具、三欄位、零治理」整體重寫為「**四類型、可全域／per-assistant、軟刪除、時間戳、決定性注入、提示快取穩定優先、規模治理**」的系統；其後 v1.2.6（停止重放被取代快照）→ v1.3.0（`memory_read` 分頁）→ v1.3.1（legacy 刪除確認）→ v1.3.2（全量注入類型）持續修補。

### 0.3 最重要的一件事

**P0-1（靜默失憶）是最要緊的「功能承諾被默默不兌現」缺陷**：`MemoryProvider.initialize()` 只在助理編輯頁被呼叫，冷啟動直接聊天時注入讀到空快取，**既有記憶整批消失於上下文而無任何提示**。上游同構問題不存在的原因是 provider 有啟動即載＋常駐刷新的生命週期。Phase 0 只補一條兜底（未初始化就 `loadAll()`）與一條回歸測試即可根治。

另一條嵌入全程的設計不變量（上游以「決定性 block builder」踐行）：**記憶注入內容不得包含任何逐輪變數**（每個 `DateTime.now()`／微秒時間戳都會讓以 system 為首的整條 prefix 快取失效）。本計畫所有注入路徑都以此不變量設計與測試。

## 1. 上游調查：kelivo 記憶系統 V2 盤點

> 來源：kelivo 倉庫原始碼與 [Releases 頁](https://github.com/Chevey339/kelivo/releases)；唯一刻意不採的二手源是 DeepWiki（查詢多次 429）。README 定位描述（節錄）：*“with auto-organize turned on, a background pipeline decides after each conversation what is worth remembering, then extracts, deduplicates and merges it into four types: identity, workflow, voice and instructions. Memories can be global or limited to one assistant … Injected memories stay stable so prompt caching keeps working.”*

### 1.1 資料模型與儲存

`lib/core/models/memory_entry.dart`（[raw](https://raw.githubusercontent.com/Chevey339/kelivo/master/lib/core/models/memory_entry.dart)）：

```dart
enum MemoryScope { global, assistant }
enum MemoryType { identity, workflow, voice, instruction }
enum MemoryStatus { active, archived }          // 刪除 = 封存（軟刪除）
enum MemorySource { manual, tool, extracted, distilled }

class MemoryEntry {
  final String id;              // 'mem_' + 8 hex（Random.secure，碰撞重試 16 次）
  final MemoryScope scope;      // global ⇔ assistantId 必為 null
  final String? assistantId;    // assistant 範圍時必填
  final MemoryType type;
  final MemoryStatus status;
  final String content;
  final MemorySource source;
  final List<String> relatedIds;     // 條目間雙向關聯（本計畫不採，§7）
  final List<String> migrationIds;   // legacy 遷移冪等鍵
  final DateTime createdAt;
  final DateTime updatedAt;          // JSON 以 microsecondsSinceEpoch 存
}
```

- 內容去重鍵 `normalizeContent()`：trim＋連續空白折疊＋lowercase。
- 儲存是**雙層**：JSON blob（`BusinessEntityKind.memoryEntry.sourceKey = memory_entries_v1`，每次寫入全表讀改寫）＋ Drift/SQLite 帶型別欄位鏡射表 `memory_entry_rows`（`lib/core/database/business_data.dart`）→ OmniChat Phase 2 只取其「payload v2、createdAt/updatedAt、軟刪除」語義，不改儲存層（§0.1 決策）。
- 使用者畫像另有 `UserProfileField`（`user_profile_fields_v1`）— 本計畫不採（§7「使用者畫像」）。

### 1.2 工具面（V1 tool surface，`memory_tools.dart`）

| 工具 | 契約要點 |
|:--|:--|
| `memory_read` | **分頁**：`limit` 預設 50、clamp 1–100；`offset`；回 `total / has_more / next_offset`；`include_archived`、`type` 篩選；提示「注入已是摘要時才需要呼叫」 |
| `memory_update` | 寫入一條（type+content 必填）；經 **Smart Add** 自動去重／合併（NEW/MERGE/CONFLICT/SKIP）；`scope` 參數只在助理寫入範圍為 `toolDefault*` 時出現；臨時對話禁止寫入 |
| `memory_edit` | 以 `mem_xxx` id 全文替換（僅建議用於過時／錯誤） |
| `memory_search_profile` | 關鍵字 AND 搜尋（clamp 1–20）＋`relatedIds` 關聯條目（上限 10） |
| `memory_delete` | **歸檔**（軟刪除），使用者可在設定恢復 |
| `update_user_profile` | 批次寫入／清除畫像欄位 |
| `chat_search` | 本助理可見歷史對話的關鍵字搜尋（排除當前對話），按助理隔離 |

舊三工具 `create_memory / edit_memory / delete_memory` 降為 `legacyDefinitions()`——只為重放舊對話與舊規則，不再對新提示註冊。

### 1.3 注入與快取穩定性（`memory_block_builder.dart`，[raw](https://raw.githubusercontent.com/Chevey339/kelivo/master/lib/core/services/memory/memory_block_builder.dart)）

- **注入位置**：注入在 **user turn 前綴**（intro 行＋`<user_profile>`＋每類一個 `<user_memory type="...">` 塊），且組裝時用 `splitInjectedPrefix` 把歷史訊息裡被取代的舊快照剝掉（v1.2.6 修復 [`7125a25`](https://github.com/Chevey339/kelivo/commit/7125a25)）。
- **行格式**：`- [2026-10-28] (assistant) 內容`——日期＝該條 `updatedAt`（本地時區 yyyy-MM-dd）；`(assistant) ` 前綴標記助理範圍條目。
- **摘要模式（規模治理）**：某類型總數 > `memoryInjectionMaxItems`（全域設定，5/10/20/30＋自訂）時輸出 `mode="summary" total=N shown=M`，取最近更新者，尾端提示 `[More entries exist. Use memory_search_profile to look them up.]`；v1.3.2（[`4588c26`](https://github.com/Chevey339/kelivo/commit/4588c26)）新增**全量注入類型**（特定類型無視條數上限）。
- **排序（決定性）**：塊內先 global 後 assistant、再 createdAt、再 id；塊間固定 `identity → workflow → voice → instruction`。
- **快取穩定裝置**：`hashBlocks()`（SHA-256 前 16 hex，profile+memory 塊指紋）、`linkBidirectional()` 刻意**不推進 updatedAt**（避免無謂的全量重注入）、組裝路徑上**沒有任何 `DateTime.now()`**。
- **防注入**：`escape(& < >)` ＋ `flatten`（摺疊空白）＋ intro 行明示內容是系統提供的資料、不是使用者本輪輸入。

### 1.4 背景整理 pipeline 與手動觸發

`MemoryPipelineService`（`memory_pipeline.dart`）：佇列單並發（上限 8、滿丟最舊）→ 每個 job **Gatekeeper（1 呼叫，判定「不值得記」即止）→ Extract（1 呼叫，抽取四類條目，prompt 內帶既有記憶防重抽）→ Smart Add（無 LLM：精確重複 SKIP；批次模式：檢索同類型候選 top-5＋最近同類補足，判 NEW/MERGE/CONFLICT/SKIP，限制同 scope）→ Profile Distiller（僅 identity 異動時）**。守衛：只在助理回合數 ≥ `memoryOrganizeEveryNTurns`（1–20）觸發；串流中跳過；同窗失敗 3 次強制推進水位；每步（gate/extract/smartAdd/distill）經 `MemoryTraceRecorder` 逐步記錄供 trace 頁審視；整理用模型另選（`memoryModelProvider / memoryModelId`）。助理級亦可**手動**觸發同管線（「整理記憶」按鈕＋狀態行）。

**成本輪廓（小模型、12k 字窗輸入）**：Gatekeeper-only ≈ 1 呼叫，完整輪 ≈ 2–4 呼叫；量級約 $0.002–0.01／次。手動觸發方案中使用者不按不花錢。

### 2.2 已核定決策與本計畫的取捨

- **全域 scope 引入**（§0.1）：評估報告 §四 當時裁定「per-assistant 隔離先維持」，依據是「重寫成本高」的推斷；上游以單一 `scope` 欄位＋寫入範圍策略實現後，Phase 2 資料模型重寫本就在動模型，引入 scope 的**邊際成本低**。預設寫入範圍仍為 assistant（老使用者行為不變），策略選項照抄上游：`alwaysGlobal / alwaysAssistant / toolDefaultGlobal / toolDefaultAssistant`（default `toolDefaultAssistant` ≈ 現行行為）。
- **四類型的錯分只影響美化、不影響可見性**：`type` 用於分組、排序與 per-type 上限，不影「內容是否注入」（全類型都會注入）。因此 legacy 匯入時**一律 `type='identity'`**（舊指令要求模型記的東西主要即使用者資料）是可接受的權衡，UI 可一鍵改。
- **存儲不搬 SQLite**：§3.18 底座覆蓋 chats/messages/provider artifacts，不含任意業務表；搬遷需動備份序列化，Phase 2 不值得。`memory_entries_v2` 之 payload 形狀與上游表欄位一一對應，日後搬遷只是換持久層（§7「儲存層 SQLite 化」）。

### Phase 1 — 治理修復（無 schema 變更；`injectMemoryAndRecentChats` 重寫）

#### M1-1 注入去除逐輪變數

- 拋棄 `DateTime.now().toIso8601String()`。Phase 1（v1 資料無時間戳）時注入區完全不含動態時間；Phase 2 起按 M2-3 以 `updatedAt` 的 yyyy-MM-dd 帶入（每條自身日期在記憶寫入期間不變 → 不破壞快取）。

#### M1-2 三層規模上限


## 6. 風險與相容性

1. **P0-1 修復的副作用**：首次冷啟動聊天多一次非同步 `loadAll()`（SharedPreferences 讀一次 JSON，量級毫秒）；兜底只觸發一次，載入後走快取零重複成本；測試釘住「同輪只 init 一次」。
2. **工具面切換**：舊對話歷史重放的 `create_memory` 事件照現況重放（歷史資料不變）；在新提示下模型改用新工具名。handler 別名保底：萬一模型仍調用舊工具名，工具照樣作用於 v2 鍵。UI/compaction case 表同時覆蓋新舊名。
3. **legacy 匯入的時間戳**：v1 無時間 → 以匯入日補（顯示為「(imported)」標記），模型看到日期會偏新；說明見 §2.2（錯型別／時間偏新均不影響可見性，UI 一鍵可改）。
4. **注入位置微調**（memory 區塊移到 workspace 之後、search 前）：改變 system 組裝順序。契約上是純重排（各區塊語義不動）；既有 prompt-caching 測試未鎖區塊順序，主以 M2-3 冪等性測試鎖住；實機驗收確認 Anthropic／OpenRouter 快取命中不掉。
5. **規模治理改變既有行為**：記錄多用戶（>per-type 上限）升級後注入進入 summary mode、32KB 總 cap 觸發尾端截斷——原本「無上限」的注入轉為可預測上限＋`memory_read` 查找路徑；設置頁可用上限／全量注入類型回調。留意 **可見性 ≠ 免截斷**：被截斷的條目本輪讀不到，但 `memory_read` 取回（非永久丟失）。
6. **整理品質（Phase 3）**：LLM 抽取／MERGE 錯誤可能污染。恢復路徑：(a) Smart Add 產物進 UI 可即時編輯/刪除；(b) last-run 狀態行顯示每次運行數量差異；(c) 完整 trace 頁屬 §7 未來項。輸出 schema 嚴格 JSON＋解析失敗退化 strict（不寫垃圾）。
7. **跨版本 payload 處置**：`memory_entries_v2` 載入全程走「缺欄位即用預設」解析（比照 `Assistant.fromJson` 的防禦載入），任何舊版／跨版本備份都不會 crash。
8. **不搬 SQLite 的機會成本**：記憶寫入的交易安全弱於 §3.18 chats 表事務（以寫入序列化佇列＋防禦解析兜底）；未來搬 SQLite（§7「儲存層 SQLite 化」）即補足，Phase 2 不承擔搬遷風險。

## 7. 刻意不導入／後續觀察項

| 上游特性 | 本計畫處置 | 理由 |
|:--|:--|:--|
| **背景自動整理**（每 N 輪 queue/watermark/trace） | §0.4 之外；記錄在案為同一 pipeline 的排程延伸，**無悔順序**：先手動再自動不丟工作 | 每 N 輪 1–4 個隱形 LLM 呼叫、+2–4 人日（queue/watermark/trace UI）；待手動整理被使用驗證後再上（含整理模型使用率數據可為證） |
| **使用者畫像（UserProfileField＋Profile Distiller）** | 不導入 | 結構化畫像是 identity 抽取的辭書化蒸餾，手動整理已抽 identity；作為畫像 UI（預設名/性別/時區…）的產品面與 OmniChat 既有「助理系統提示＋模板變數」重疊；待記憶普及後評估 |
| **`chat_search`（跨對話回憶搜尋）** | 不導入 | 需歷史訊息全文檢索入口（SQLite/Drift 查詢可行，但要新增檢索面與結果卡 UI），且 OmniChat 已有「最近聊天＋§3.14 L1 `<conversation_summary>`」近似路，收益／成本比尚低 |
| **`relatedIds` 條目間關聯** | 不導入 | 上游為此特設維護規則（`linkBidirectional` 需雙側同步且刻意不推進 `updatedAt` 以護快取），維護成本可見；<200 條規模下關聯檢索收益低 |
| **`memory_search_profile`（關鍵字搜尋工具）** | 不導入 | per-type 條數上限＋全量注入＋`memory_read` 分頁在 200 條規模已足；若未來記錄數爆量超出注入治理能力，本工具即第一補強項 |
| **向量檢索** | 不導入 | 上游明證同規模關鍵字檢索已足（§1.6） |
| **prompt 模板自訂 UI**（上游 7 個可編輯模板） | 不導入 | 本計畫刻意只保留**不可編輯的純常數**（§3.15 精神）；待有真實調整需求再評 |
| **完整 trace 檢視頁** | 不導入（簡版 last-run 狀態行代替） | trace 基礎設施（Recorder＋專頁）成本高；手動整理單發流程以 snackbar＋last-run 狀態行已足覆蓋審視需求 |
| **儲存層 SQLite 化** | 後續選項（§6 風險編號 8） | 待 §3.18 業務表體系成熟或檢索需求出現時再做；`memory_entries_v2` payload 與上游 `memory_entry_rows` 欄位一一對應，遷移只是換持久層 |
| **上游 user-turn 前綴注入＋`splitInjectedPrefix`／`hashBlocks`** | 後續選項 | 上游以完整機制踐行（快照寫進歷史＋組裝時剝離舊快照；v1.2.6 已修防重放）；OmniChat 實測「記憶寫入損耗前綴快取」不明顯前先採保守方案，實測顯示傷快取再升級 |
